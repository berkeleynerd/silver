- A program expressed as valid Silver can never be rejected as non-Silver. If it compiles, it proves. Silver has two assurance modes, each defined by explicit, decidable rules: a **strict** program satisfies the derived capacity rules and proves by construction, so its guarantee requires no per-program prover run; a **loose** program is valid Silver outside those rules and compiles only when its own proof run succeeds. A loose program whose proof run ends in a resource or prover outcome does not compile; that outcome is reported as such and never as success. In loose mode Silver guarantees no less than GNATprove's verdict on the same source.
- “Proves” means automatic discharge of every required Bronze and Silver obligation, without developer intervention.
- Silver is a subtractive profile of SPARK: it removes or restricts constructs without adding syntax or changing their meaning.
- Silver program authors write actual Ada/SPARK source. No alternative authoring representation constitutes Silver source.
- Silver program authors never write preconditions, postconditions or proof annotations. Compiler and Silver-owned library authors may use SPARK contracts and proof annotations.
- The only permitted pragma in Silver program source is `pragma SPARK_Mode (On);`.
- Assurance facts about Silver programs must be derived automatically from their declarations, types, expressions and executable control flow, together with verified contracts of admitted library operations and documented interface assumptions at approved trusted external boundaries. Silver program authors supply no additional assurance facts.
- Safety conditions must be established throughout the complete call chain, using executable guards wherever necessary.
- Guarantees must cover every permitted input, execution path and combination of admitted constructs.
- Language membership is determined by explicit, decidable rules—not by whether a particular prover run succeeds. A program's assurance mode is determined the same way.
- The source admitted, proved and compiled must be the same source. Hidden annotated replacements are forbidden. Library specifications and implementations selected for verification and compilation must correspond. Trusted external dependencies and their assumptions must be documented.
- The assurance guarantee must be proved for the language and its composition rules. Passing examples is insufficient. Every language change must establish the guarantee for the resulting admitted language and all its permitted compositions.
- Proof success must never be obtained by silently changing behavior, narrowing declared input domains or suppressing obligations.
- Rejection of a valid Silver program, or proof failure of a strict program, is an implementation defect, not permission to weaken the guarantee. For a loose program, a resource outcome or an inconclusive prover result is not a defect; a definite non-proof with resources remaining is recorded and investigated as a potential defect.
- Fixed editions of the Ada and SPARK specifications define inherited language meaning; this Oracle defines the additional restrictions and guarantees.
- Changes to this Oracle require the human owner’s explicit approval. No implementation decision can override it.
- Maintain the current Silver language specification, constrained by this Oracle and the inherited Ada/SPARK meaning, with a corresponding machine-readable catalogue of admitted constructs and library operations, their conditions, permitted argument forms and compositions. The specification, catalogue and compiler must agree; everything not explicitly admitted is excluded.
- Before 1.0, Silver is one evolving language, without a compatibility obligation to earlier revisions. Changes must be explicit and reflected consistently in the specification, catalogue, implementation, proofs and samples. Prioritize foundations necessary for the current language; defer independently addable release and deployment hardening until the intended use requires it. This does not weaken the assurance required for currently admitted programs.
- Language restrictions and implementation resource limits must be explicit, with their purpose documented. Temporary scope limits must not be presented as requirements inherited from Ada/SPARK or as inherent limits of an admitted operation. The strict-mode rules and the hard limits that bound both modes must be documented separately; a limit whose overflow a tool would not detect is a hard limit in both modes.
- Admitting a library operation does not admit other operations of its package or other language features used by its implementation.
- Admitted operations with external effects must specify their observable behavior, failure outcomes and environmental assumptions. Assurance must cover the specified outcomes under those assumptions. External failure must not redefine language membership, excuse required proof obligations or be represented as successful completion of the requested effect.
- Both MacOS and Linux will be supported with patch-level version differences allowed. (Same major and minor version) Alire is used to manage the toolchain.
- Linux is the primary implementation and validation platform. macOS support is secondary; native macOS validation is handled independently and does not block completion of the work performed in the Linux environment.
- The Silver compiler and all Silver-owned runtime and library implementation code must be implemented exclusively in SPARK and verified to both Bronze and Silver levels. This implementation code may use SPARK features beyond the Silver application profile.
- GNAT, GNATprove, Alire, and existing operating-system/runtime libraries remain trusted external dependencies. The verified-SPARK implementation requirement applies to all Silver compiler and Silver-owned runtime and library implementation code; Silver-owned wrappers receive no exemption.
- Lean 4 is approved for machine-checked proofs of Silver's admission and composition rules, decidable language membership, universal safety guarantees, termination and, for strict programs, completeness of automatic obligation discharge, and functional correctness and semantic preservation of the Silver compiler and Silver-owned runtime and library implementations.
- Lean proofs must establish correspondence between their formal models, the actual SPARK compiler and Silver-owned runtime and library implementations, and the authoritative Ada/SPARK source. Proving a separate model alone does not establish implementation correctness; proving safety alone does not establish automatic proof success. The strict-mode rule is part of that correspondence, so the compiler's reported mode is correct.
- Lean supplements GNATprove and does not replace the requirement to verify all compiler and Silver-owned runtime and library implementation code to Bronze and Silver levels. Lean proof artifacts are neither compiler or library implementation code nor an alternative representation for authoring Silver programs.
- The Lean version must be pinned and trusted assumptions explicitly documented. Lean proofs must contain no unfinished proofs or unproved project-specific axioms and must be checked automatically during project validation. Compiler and Silver-owned library authors may develop proofs interactively; Silver program authors must never need to intervene in proof.
