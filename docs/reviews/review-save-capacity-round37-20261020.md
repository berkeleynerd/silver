### Material review finding: allocator-raise callback qualification

The original note's blanket claim that C allocations cannot dispatch
asynchronous callbacks was too broad. CAML_FROM_C excludes normal allocation
dispatch, but an allocation failure can enter `caml_raise_out_of_memory`.
`runtime/fail_nat.c:63–87` processes pending actions before its nonreturning
exception transfer; `memory.c:865–871` exhibits a native allocation-failure
entry. The reviewer independently identified this distinction after the first
successful checker run and supplied the exact source join to the author.

The numerical bound survives: if this path dispatches an admitted signal save,
the nested save receives its existing global e/r charge. The callback cannot
return normally, and the raising path ultimately transfers out of the original
C walk or terminates. The abandoned walk cannot resume and revisit a record;
its already attempted increment and allocation prefix stay charged. The
no-callback/subsequence argument must therefore be stated for a **normally
continuing** walk. This does not prove safe allocator-failure recovery from an
unfinished custom block, and does not enable failed-service capacity.
