## Findings checked

**Expression visits.** The aggregate retains the earlier at-most-two
source-child translation argument. It additionally charges String inequality's
possible not node, all three parser-flattening replacement nodes without
credit for removed nodes, and two generated reads per captured bound. The
capture initializer occupies its own preceding declaration and does not get
replayed through every read. Thus `2*(X+U+3P)+2G` is conservative under those
frontend shape premises. The inspected preliminary SPARK rewrite changes
ordinary aliases to their ultimate entity but does not expand this expression
forest; the other rewriting cases require excluded constructs.

**Uniform local cost.** Type_Of_Node returns an existing binder/builtin type
or constructs at most the charged three-node map/type shape, excluding the
separately named symbol/module caches. Summing the concat core, expected-type
allowance and one full String conversion gives `(110,54,80,943)`. Each other
local case plus its applicable boundary/predicate allowances is componentwise
smaller. The predicate wrapper creates one equality call on the Boolean result
and True, plus a possible label; it does not retranslate the supplied child.
The known scalar boundary row covers the static assignment/declaration targets.
Dynamic loop-index types do not introduce a dynamic source target conversion.

**Literal definitions.** The distinct translated literal counter K remains
separate from the literal type-entity counter. The earlier definition formula
is conservatively bounded by `K*(23,13,10,75)+H*(7,3,6,40)`: its optional
connection node/list and extra occurrence fit the fixed K term, and
`5L+max(L-2,0) <= 6L`. Empty definitions fit the fixed term as well. Literal
per-use work stays within the uniform expression row. The type pass still
uses its larger independent `K_literal <= S+3A+5P` bound.

**List composition.** Ignored nodes return Void or may receive a declaration
location label. They still incur list visitation and possibly the executable
list's outer label, as the aggregate now charges. The Append helper flattens
only an immediate statement sequence. Ordinary generated declarations have
at most two immediate entries; source statements receive their positive
location wrapper, preventing subtree-wide flattening. Each ordinary entry
has one containing list and is translated once under no loop unrolling.
The frontend-allocation input A_Main therefore bounds the visited entries,
including ignored/generated entries. If/elsif and loop nodes bound list
count by `2+2*A_Main`; an absent else is conservatively included.

The per-entry vector `(2,0,2,6)` and per-list vector `(1,1,1,5)` consequently
sum to `(4*A_Main+2,2*A_Main+2,4*A_Main+2,16*A_Main+10)`. The Void occurrence
allowance covers discarded/flattened sequence structure without claiming
to charge a second translation of nonempty child cores.

**Skeleton and entity/type composition.** Source Integer declarations and
generated captures use the Integer row; String declarations use the String
row. Static generated subtype declarations are bounded by `R+D_s` and add
no source expression replay. Assignment rows retain their internal conversion
work, while initializers/RHS values are in the expression term. Calls,
condition points, branch warning wrappers and loops use their prior closed
rows. The largest String frame row dominates both Integer rows and the String
Not_Written row; `F*(D+4)` covers every possible distinct modified source root
and the four concrete output globals per loop.

The object/type pass terms, array attempt count `D_s+K_literal`, single
representation miss and their close counts match the preceding component
derivations. Counting the miss even if predefined setup already paid it is
conservative. The declaration/list terms deliberately overlap some
label/Void charges but do not omit an additional nonempty child translation.

## Remaining limits

The report does not supply A_Main; a source-derived frontend allocation
bound is still needed. It also excludes memoized entity-symbol/module setup,
the enclosing Main subprogram definition/completion/VC wrapper, predefined
and selected dependency translations, and imports. Their counters and source
identity premises remain part of the complete producer/capacity task. The
closed ordinary-Main transfer must not be interpreted as permission to change
admission before those obligations are addressed.
