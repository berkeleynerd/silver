**The candidate source supplies useful finite output components, but no complete

## Selected command and correspondence

The selected zero-step command is unchanged:

```text
cvc5 --prenex-quant=none --stats-internal %f
```

`--stats-internal` calls `setStatsDetail`, which enables `statistics`. Defaults
leave `stats-all`, `stats-every-query`, `print-success`, `use-portfolio`, model/
proof dumping, pivot statistics and ITE simplification off. Verbosity is zero,
which still permits warnings. These defaults must remain true after task
commands and automatic option selection; CLI tokens alone do not prove that.
The no-StepRegexp proposal changes Why3 parsing, not this solver output.

The separately inventoried packaged binary embeds version 1.3.2 and this exact
revision. That is build-identification consistency, not a proof of binary/source
behavior, a clean source tree or the build recipe. In particular, the retained
server's `PATH=/usr/bin:/bin` and bare-name `execvp` remain unattached to the
packaged executable. This packet supplies candidate-source behavior for a
prospectively fixed executable/configuration, not a historical solver execution.

Numeric bounds below require ordinary represented C++ objects, returning normal
formatting services, decimal integer formatting, defaultfloat precision six,
zero width and the C numeric locale. They do not establish internal arithmetic
validity, finite solver time or resource sufficiency. A concrete attachment must
also identify build modes and preserve these stream properties. No arbitrary
output truncation, step cap, time limit or post-run admission test is proposed.

## The normal response includes a second command

The retained `cvc5.gen` sets `supports_smt_get_info_unknown_reason`.
`smtv2.ml:777–784` emits `(check-sat)` followed by
`(get-info :reason-unknown)`. The counterexample-off task excludes the following
model query. A single-goal task invokes this pair once, and the printer's
incremental branch can invoke it once more (`:804–831`). Thus use the
prospectively derived pair count J; J=1 additionally requires the selected
nonincremental task join. Static preludes must not add unrelated commands.

With SMT-LIB output preserved, `CheckSatCommand::printResult` emits `sat\n`,
`unsat\n` or `unknown\n`. `GetInfoCommand` constructs a two-element S-expression.
On unknown, its reason comes from the finite `UnknownExplanation` enumeration,
lowercased by `SolverEngine::getInfo`. On sat or unsat, it prints the fixed
recoverable error:

```text
(error "Can't get-info :reason-unknown when the last result wasn't unknown!")
```

Including line feeds, the combined pair sizes are at most **82 / 84 / 47** bytes
for sat / unsat / unknown. Hence `Q_result <= 84J`. The 67-byte error payload
has a 78-byte wrapper result. This is expected candidate behavior for the
selected reason query; it is not a new proof failure. The API's fresh result
stringstream uses the global printer-language default generated by
`mkoptions.py`; the driver's SMT-LIB language selection is part of this join.

Other successful declarations/assertions emit no success line while
`print-success=false`. An admitted task language/driver relation must establish
which commands occur; accepting arbitrary SMT-LIB would also admit echo, model,
proof, get-option, get-info/all-statistics and option-changing output paths.

## A prospective statistics dump interface

`command_executor.cpp:81–105` prints **both** the solver and TermManager
statistics, separately. Each record is `name + " = " + value + LF`.
`Statistics` exports all registry entries before its iterator filters internal/
default values (`api/cpp/cvc5.cpp:5108–5159`); filtered entries can therefore
still cause construction failures. This byte account does not cover those
allocations. Repeated registration under the same name shares one map entry
within a registry; names shared by the two registries can print twice.

For a prospective superset of records in one complete two-registry dump, let:

- S be its record count and L_names its name-byte sum, counting the registries
  separately; I/D/T count integral/average/timer records.
- L_strings bound all other string-valued statistic bytes.
- For each histogram h, K_h bound its distinct exported keys and L_keys_h their
  total printed bytes. These are source/configuration domains, not counters
  sampled after execution.

Then the ordinary printer gives:

```text
Q_stats <= L_names + 4S + 20I + 13D + 22T + L_strings
           + sum_h (4 + L_keys_h + 24K_h).
```

`IntStat` is int64; integral references and sizes export through int64. Twenty
bytes covers either signed64 decimal or uint64 decimal. A defaultfloat binary64
at precision six fits 13 bytes, including sign/exponent; normal inf/nan tokens
also fit. This is a formatting bound, not a finite-value or JSON claim. Timers
return a uint64 result converted to decimal plus `ms`, at most 22 bytes; no
elapsed-time limit is inferred. Arbitrary string values remain separate.

The histogram printer emits `{ `, zero or more `key: uint64` entries separated
by `, `, and ` }`. Its exact length is
`4+L_keys+22K+2*max(K-1,0)`, bounded by the displayed formula.
`getViewer` traverses positive buckets and inserts into a string-keyed map, so
duplicate printed keys collapse for the ordinary printer.

The lexical source scan finds 354 direct registration call sites in 1,641
`.cpp`/`.h` files: 185 use a literal first argument and 169 use expressions.
This is **not** a bound of 354 runtime records. Examples requiring an argument
domain are `preprocessing:: + name`, equality-engine name prefixes, theory
prefixes and the public-statistics loop. The retained
`registration-sites.json` identifies every matched call and expression. A
complete registry certificate must join constructor invocations and prefix
domains to the particular printed registries, including late registrations.

The two `registerValue<std::string>` sites both name `driver::filename`: public
registration and `SolverEngine::setInfo`. No string ReferenceStat site occurs
in this direct-call inventory. Under its registration/option closure and no
task `set-info :filename` override, the solver value is the input filename F
bytes; the TermManager's public default remains empty. This specializes
`L_strings<=F`. The command-line path's prospective length still needs the Why3
filename construction and task-name join; a current filesystem observation is
not that proof.

The following tables enumerate all literal return spellings, including

For ordinary printing, the named enum's streaming operator calls that function.
They bound **one histogram value**, excluding its name and record wrapper:

These allowances do not imply every key is reached, or that all corresponding
statistics are selected. They do not assert behavior after an invalid-enum
assertion. The remaining histogram types are internal/API Kind, TypeConstant,
ProofRule and ProofRewriteRule. Their generated printers and, for internal
Kind, printer-language dispatch need their own finite output-domain attachment.
The full exact source archive is retained to make this remaining work bounded.

Four matched histogram sites use uint32 keys: `ite-simp::inSmaller` and the
arith `pivots::sat`, `pivots::unsat`, `pivots::unknown` families. A type-only
ordinary value allowance would be `4+34*2^32 = 146,028,888,068` bytes per
histogram. That allowance is not evidence of such an output or a selected
capacity impossibility. In fact:

- Every pivot insertion is guarded by `collectPivots`, whose default is false
  (`theory_arith_private.cpp:3205–3267`).
- The ITE histogram is instantiated/updated through `ITESimplifier::simpITE`.
  Its selected preprocessing caller is guarded by `doITESimp`, also false by
  default (`process_assertions.cpp:412–420`; `ite_simp.cpp:123–146`). The source
  option-occurrence inspection found no automatic true assignment in
  `set_defaults.cpp`.

Preserving those option values and excluding alternative pass entry points
therefore removes these active bucket domains. Default filtering also omits
empty registered histograms. If ITE simplification is later selected, its two
insertion sites use 1 or the minimum of two constant-leaf-vector sizes
(`ite_utilities.cpp:1152–1171`); a useful bound then needs the generated/rewrite
term domain. Counting Ada source tokens alone does not establish it.

## Errors, warnings, repeated dumps and termination

The following transfer bounds include LF and assume the indicated ordinary
printer route. They close the wrapper, not its payload producer:

| Family | Byte bound |
| --- | --- |
| Command failure/recoverable failure with m-byte message | `11+2m` |
| Main API exception with m-byte virtual streamed text | `11+m` |
| Main option exception with m-byte message, including help line | `67+m` |
| Located parser error, message m and filename F, LP64 line/column | `68+F+m` |
| File-open ParserException | `44+F` |

The SMT2 command printer doubles quotes, giving `2m+2` for its quoted string.
Main's exception wrapper inserts the message directly instead. A parser
exception overrides virtual `toStream` with `Parse Error: filename:line.column:
message`; each unsigned long takes at most 20 decimal digits on LP64. A
competition build can add `unknown\n` to main's caught exception branches;
charge eight additional bytes if that mode is in scope.

`CheckSatCommand` and other commands catch `std::exception` and store `what()`.
Fatal command failure stops the ordinary loop; recoverable failures can
continue. Parser errors leave the noninteractive loop for main's handler.
Thus a finite source-derived command count bounds ordinary per-command status
occurrences, but it does not bound their messages. Parser messages can include
token text; API/theory errors can include rendered terms or strings derived
from solver state. File-open text is separately closed above. One blanket
constant for all `what()` messages is unsupported.

Warnings remain enabled at verbosity zero: `WarningChannel` initially targets
stderr, and `Env::warning()` selects `verbose(0)`. Parser warnings include path,
line/column and message; theory warnings can print terms, reconstructed models
or failures. Their selected reachability, occurrence counts and term-rendering
byte sums remain a separate W term. Neither `--stats-internal` nor the absence
of verbose flags makes W zero. Assertions, direct fatal diagnostics and any
enabled output tags likewise belong in the residual output-family closure.

On the ordinary nonportfolio route with no task-driven statistics query/reset
and `stats-every-query=false`, there is one normal `flushOutputStreams` dump.
A failure after a prefix of it can enter main's API-exception catch and attempt
another full dump. Therefore allow **two** ordinary dump attempts in that
conditional route, charging abandoned prefixes. Exceptions from a catch body
are not caught by the earlier sibling catches; termination output can follow.
This local two-dump condition does not borrow or renew Why3's global callback,
save or abort budgets.

`signal_handlers.cpp` prints statistics from timeout, SIGTERM, SIGINT, illegal
instruction, segfault and C++ termination handlers. Timeout/SIGTERM/SIGINT/
illegal-instruction/C++-termination release messages cost 29/29/26/38/96 bytes;
segfault/debug paths add
address/context/program-name text. A conservative source-literal envelope for
one handler's **own text** is `1350+4P0+98`, with P0 the program-name length:
1,350 is the sum of all quoted string tokens in that source file, including
both build branches; four PID decimals cost at most 80 and one hexadecimal
pointer at most 18. This deliberately overcounts mutually exclusive text.
Statistics and any preceding diagnostic are separate.

Signal-safe statistics use a different printer. Integral values still need
at most 20 bytes, and timers 22, on its valid conversion domain; its double
routine uses at most 41 bytes. It prints each positive bucket directly, so the
normal map's duplicate-key collapse cannot be reused without a valid enum/key
domain. There are also genuine caller preconditions: signed printing negates
negative int64, excluding INT64_MIN from a defined source execution; double
printing casts to int64, which needs a finite representable operand. Merely
being a stored double does not prove that. Signal entry must preserve the
registry/vector objects it traverses. No complete signal-path guarantee is
claimed from these local formatting counts.

Finally, `cvc5terminate` restores and calls the saved C++ `default_terminator`
after its message and statistics. Its runtime output is **not** bounded by the
CVC5 source literals. The exact static runtime handler/type/message behavior
needs a byte interface, as do any pre-handler fatal diagnostics. General trust
in a correct runtime with valid inputs and sufficient resources does not
identify these output operands or their lengths. No proof of the entire C++
runtime is requested here. The number of terminal activations must be derived
from the selected signal/environment behavior, not from Why3's two callbacks.

## Composition and useful-domain consequence

A candidate prospective certificate can supply finite permitted registry/name
sets, histogram spelling sets, F, task pair/command counts, exception-payload
byte sums, warning bytes, dump counts and termination/runtime bytes. Its
inclusion argument must relate them to every selected generated task and
continuation before running the tool. With ordinary and safe dump bounds
Q_stats/Q_safe, a sufficient interface is:

```text
q_cvc5 <= 84J + D*Q_stats + H*Q_safe
          + E_command + E_main + W
          + H*(1350+4P0+98) + R_runtime + X_other.
```

E_command includes the doubled quote bounds and multiplicities; E_main includes
the appropriate main/parser/option wrapper, not a second arbitrary catch budget.
H counts prospective terminal entries, and X_other closes the remaining direct
output families. Per-dump differing envelopes can instead be summed. The
conditional ordinary route supplies D<=2. No numeric zero is substituted for
unknown W, payload, terminal or residual terms. The result is a byte interface,
not a termination, completion or automatic-discharge theorem.

For the five current cases, the previously derived optimistic uniform q
ceilings remain 1,156 / 1,391 / 2,229 / 20,074 / 26,766. Even the **upper
allowance** 18,539 for one complete InferenceId histogram exceeds the first
three ceilings; it leaves only 1,535 / 8,227 bytes in the last two before its
name, other records or error paths. This shows that a complete-enum allowance
alone cannot make those sufficient guards useful in the first three cases.
It is not a lower bound on actual output or evidence that useful admission is
impossible. A proved smaller reachable-key set or a tighter downstream
capacity account could change that conclusion. The disabled uint32 families
must not be used to manufacture a selected impossibility.

Once each selected solver has a proved per-attempt bound, the accepted interface
remains `O=max(A,N)*q`, with A=208/173/108/12/9 and N=194/161/98/11/5, or its
proved multiplicity-weighted per-attempt refinement. CVC5 components alone
cannot instantiate the common three-solver q. The intended #88 configuration
still needs parallelism at least three; the historical j=1 cuts and this
per-process analysis do not establish its parallel scheduling join.

The next bounded work is to join the generated task/option language and finite
registration/name/key certificate, then close W and caught/uncaught diagnostic
payloads for that same scope. Source/executable correspondence remains separate.
