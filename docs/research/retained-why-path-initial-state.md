## The active table operation has a small callable boundary

`Theory.id_to_path` and `id_to_th` are private closure locals
(`theory.ml:472–492`). The accepted private-writer census is reused: these
owners call `Wid.mem`, `Wid.set` and `Wid.find`; they do not expose a bucket
array, copy of the table, table iterator or user-supplied mutation callback.
The `Sid.iter` callback inside `store_theory` is the displayed `Wid.set` closure.
The remaining prefix inside `store_path` only constructs the component list
with `(@)` and `List.rev`; its callbacks are the same allocation/pending
interface below. Thus including a saved, not-yet-installed payload in an outer
`store_path` frame does not add a path to either cut.

`Ident.Id` supplies `tag id = id.id_tag` (`ident.ml:164–177`). `Weakhtbl.Make`
selects `Ephemeron.K1.Make`, with hash equal to that tag and equality comparing
the two tags, and `set = replace` (`weakhtbl.ml:67–91`). Thus a hash/equality
call reads integer fields; it cannot invoke a method or closure from the key.
This argument does not require distinct tags or physical identifier freshness.

The relevant Ephemeron bodies are completely explicit:

| Operation | Callable successors while its saved table state exists |
| --- | --- |
| `resize` (`ephemeron.ml:195–211`) | `clean`, array length/make/access, integer operations and local `insert_bucket` recursion. The saved `odata` remains local. No user hash/equality is called during rehash: cached `hkey` values are copied. |
| `clean` (`:159–172`) | `H.check_key`, scalar size updates, local recursion and `Cons` allocation. K1 `check_key` selects the native ephemeron check. |
| `replace` (`:315–335`) | The tag hash, K1 equality, `set_key_data` or K1 creation, local bucket recursion/allocation, and possibly `resize`. The old bucket `l` is local. |
| K1 adapter (`:492–560`) | Ephemeron creation/get/set/unset/check, option allocation and the tag equality above. No table payload is executed. |

Generated allocation/poll/raise calls are included. In particular native
ephemeron creation and getters explicitly process pending actions
(`weak.c:128–139,326–342`), even without a collection. It would be invalid to
replace this table with a claim that these functions cannot call back.

The ordinary native interfaces here are the accepted allocation/collection,
scalar/array/weak storage and raising contracts **applied to these particular
operations**. Their owned writes do not manufacture an OCaml application
entry. Collector timing/root/context/destructor callbacks and pending dispatch
are exposed by the initialization/client facts above. No arbitrary custom
compare/hash, Marshal, loader, stack-statistics or foreign callback is selected
by the integer tag and ephemeron-container operations. Runtime failure can
raise or terminate; no capacity/success assumption is made for those outcomes.

## Why a pending callback cannot reach either cut with the frame intact

The cut entries are ordinary synchronous source control, not registered runtime
callbacks. `Gnat_main` finishes initialization and registration, then invokes
`Gnat_checks.iter (handle_obj c)` (`gnat_main.ml:332–347`). `iter` folds the
checks and runs its supplied function (`gnat_checks.ml:507–509`). The other
GNAT caller is ordinary `ending`'s reporting pass (`gnat_main.ml:274–275`),
also absent from the signal handler. The four captured PCs are entry at
`0x530a10`; scheduling, driver preparation and prover-request guard counts are
zero. This distinguishes their registration stop from the later reporting call.

For PID 17869, `graft_proof_attempt` returns before the scheduled callback and
`run_idle_handler` (`controller_itp.ml:641–652`). GNAT's `S.idle` synchronously
runs the given function in a while loop (`gnat_scheduler.ml:10–12`);
`idle_handler` calls `build_prover_call`, which calls `Driver.prove_task`
(`controller_itp.ml:412–440,517–536,578–584`). `prove_task` calls
`prepare_task`; its local `apply` is passed only to `List.fold_left`
(`driver.ml:372–390,490–494`). The fresh observer stops at that local closure's
entry `0x5d7aa0`, with visited directives
`counterexamples_dependent_intros`, `inline_trivial`. The inherited registration
endpoint field in the inline plan is not used as the actual stop. Thread yield
does not run this scheduler's idle or timeout functions.

Now suppose a pre-cut restore-table operation still has a resumable frame at
one of those entries. Its direct successors above cannot enter either cut.
There is one OCaml worker, so the putative path must run through one of its
pending/native clients. Their possibilities are:

1. **Collector/native owners and SIGVTALRM.** The selected owners perform their
   described runtime/storage operations. `Thread.preempt` calls `yield`
   (`thread.ml:81–104`); the one-worker native guard returns without scheduling
   another OCaml application (`st_stubs.c:723–740`). No cut entry is a successor.
2. **SIGINT save.** `save_session_and_exit` ignores the three termination signals,
   calls `Gnat_checks.save_session`, then `exit` (`gnat_main.ml:298–309`). The
   helper directly calls `Session_itp.save_session` (`gnat_checks.ml:752–753`).
   Its synchronous callbacks traverse session data, explain/shape tasks, back
   up files and serialize (`session_itp.ml:2212–2245` and the accepted save
   source-ownership argument). They neither run `ending`, a controller
   callback, the work scheduler, a driver transformation nor a parser. The
   serializer's `%a` callbacks are its fixed save helpers; formatter queues
   retain tokens rather than preparation callbacks. Shape/term constructors
   may allocate or register identifiers; that is irrelevant to this narrower
   **no cut-entry** result. Their primitive/native successors return to the
   same classified pending clients. This does not import the old PID's numeric
   domain or assert bounded cost of saving a pre-cut session.
3. **Exit while the signal frame is active.** Its available hooks are the
   retained ordinary output owners, not controller/preparation callbacks.
   In addition the still-true once gates independently exclude execution of
   either hook before this cut, by the persistent-chain argument above.
   Terminal `flush_all` only operates on channels. The accepted native lifetime
   source contracts and this invocation's zero cleanup selector add no such
   application entry. A raised exit/output exception takes case 4.
4. **Exception transfer.** Pending dispatch returns an exception result and
   raises it at the interrupted operation (`signals.c:260–305`,
   `fail_nat.c:63–87`). `resize` and `clean` contain no receiving catch. A handler
   outside them runs only after their frames have been unwound. `replace` does
   have a `Not_found` catch around `replace_bucket`; it can install its supplied
   cell and resize, but it does not call a cut entry. The resize in the handler
   is outside that catch. An outer parser/controller catch may continue and
   eventually schedule work; its unwound table frames cannot resume afterward.
   A caught exception inside a save continues that save's fixed helpers. No
   arbitrary diagnostic callback is dispatched by ordinary unwinding while
   preserving a resumable table frame. If the runtime has no receiving OCaml
   trap, uncaught processing may still report before terminating, but there is
   no OCaml continuation that reinstates the abandoned table operation. The
   absence of that resumption, rather than zero diagnostic work, is the fact
   needed here under the same faithful exception/stack relation.

This exhausts the local active-operation interface. It is a call/control
argument, not a claim that every pre-cut application helper has zero native
effects. It permits arbitrary earlier signals, interrupted/failed table writes,
continued outer catches, weak clearing and later scheduling. It does not use a
no-signal assumption, no-allocation assumption, signal count or old identifier
no-wrap argument. Source startup/client binding, native owner effects and
faithful exception transfer are essential; merely asserting configuration
flags would not supply this proof.

## From no suspended operation to initial payload completeness

The table array is reachable through its private owner. During resize an old
array can also be reachable through `odata`; during replacement an old bucket
can survive in `l`. The preceding argument excludes both resumable operations
at the cut. No owner API publishes those arrays/buckets into another callback,
worker or application continuation. On normal return only the current table
remains as a future mutation root. On escaping failure, abandoned local arrays
do not become callable continuations. Uncollected bytes or a collector's
temporary roots cannot cause an abandoned OCaml operation to resume.

This does **not** assert transactional resize. A previously interrupted resize
may already have published a partial array. That actual current array is exactly
the one whose cells were completely inventoried in
[the accepted input packet](retained-why-path-input-inventory.md). The argument
therefore needs neither old/current equality nor successful completion of all
past mutations.

Lookup tests the cached hash before key equality, and both derive from the
immutable tag. The accepted full current-array census has unique cached hashes;
for every serialized tag it contains zero candidates or the one fully decoded
candidate. Two tags per case have candidates: an empty path and a one-component
six-byte path. Other current payloads remain partially decoded. They cannot
become candidates for a captured tag merely by being moved during a later
resize: cached hashes are copied unchanged. Collection may remove a candidate
and select the immutable fallback. A later writer can install a new payload;
that writer belongs to the separate continuation bound.

Hence the initial contribution is completely covered by the displayed paths
and fallbacks. The former `no suspended Theory resize` guard is discharged at
these five cuts within the named relation. The per-tag initial bound joins any
later uniform payload bound at `max(6, R_later)`. The initial weighted sums are
not whole-interval U and do not certify future chosen bindings remain unchanged.

All current-global payload maxima, actual later writer/library origins,
whole-interval R/U and complete save capacity remain outside this result.
Native path-list/String construction and the remaining formatter/storage/error
contracts retain their own owners. Oracle, admission, installed tools and pins
are unchanged; production #88–#94 is unstarted and PR #121 remains draft/unmerged.
Independent aggregate review and integration are lead-owned.
