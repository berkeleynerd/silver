# Planning and tracking

Adopted on 2026-10-15. Work items and their status live in GitHub issues on the
Silver board; direction and decisions stay in the repository, versioned with the
code they govern. This record defines where each kind of fact lives, the board's
structure and the routine agents follow. The owner reviewed and agreed this
structure on 2026-10-15; [Migration](#migration) records how it is applied.

## Where each fact lives

Each fact has one home. Other places link to it rather than restating it.

| Fact | Home |
| --- | --- |
| Guarantees and their amendments | [oracle.md](../oracle.md), changed only with the owner's approval |
| Supported language and admitted constructs | [language.md](../language.md) and the [catalogue](../catalogue/silver.json) |
| Workflow, validation and review rules | [development.md](../development.md) |
| Direction: the milestone sequence, deferrals and their reasons | [roadmap.md](../roadmap.md) |
| Owner decisions and authorizations, with dates | [session memory](session-memory.md) |
| Capability records, evidence and review reports | `docs/` and [docs/reviews](reviews/) |
| Rosetta assessments, inclusion policy and the progression | [rosetta/coverage.json](../rosetta/coverage.json) and [rosetta/progression.md](../rosetta/progression.md), generated by `rosetta/refresh.py` |
| Work items, their status, review findings, follow-ups and handoffs | GitHub issues on the Silver board |

Issue text never authorizes work or amends a guarantee. When the owner decides
something in an issue discussion, record the decision in the session memory and
link the issue.

## The board

The board is the private user project
[Silver](https://github.com/users/berkeleynerd/projects/6), owned by
`berkeleynerd` and linked to this repository.

**Fields**, besides GitHub's built-in ones (assignees, labels, milestone, linked
pull requests, parent issue and sub-issue progress):

| Field | Type | Values |
| --- | --- | --- |
| Status | Single select | Backlog, Ready, In progress, In review, Done |
| Stage | Number | A stage issue's current position in the progression |
| Constructs | Text | Construct identifiers a stage adds, as in `rosetta/assess.js` |

Backlog holds proposed items the owner has not authorized, and Ready holds
authorized items not yet started. In review means awaiting validation or an
independent review.

An owner authorization, pause or revocation counts as recorded only when a dated
entry in the [session memory](session-memory.md) on `main` states it. Comments on
the affected issues cite that commit, and the board's statuses change in the
same step: an agent moves an item to Ready only once its authorization is on
`main`, and a pause or revocation returns the affected items to Backlog. A direct
current owner request also authorizes work; record it on `main` the same way
before claiming the work, without waiting for a separate Ready transition or
approval.

**Labels** carry the kind of item, so agents can filter with `gh issue list`.
They replace GitHub's default labels.

| Label | Meaning |
| --- | --- |
| `type: work package` | A unit of milestone work with scope and completion criteria |
| `type: finding` | A review finding: a defect or an assurance gap |
| `type: follow-up` | A conditional follow-up from a review disposition or delivery |
| `type: stage` | A Rosetta progression stage |
| `type: decision` | A question that needs the owner: an Oracle amendment, an authorization or a policy choice |
| `severity: blocker`, `severity: medium`, `severity: low`, `severity: info` | A finding's severity, matching the review reports |
| `area: language`, `area: assurance`, `area: compiler`, `area: runtime`, `area: tooling`, `area: docs`, `area: planning` | The part of the project an item changes |

**Milestones**: one GitHub milestone for each committed delivery batch, named
as in the roadmap. Owner-authorized successor planning may also create one
provisional milestone, clearly marked as proposed with implementation issues
in Backlog. Its existence does not authorize implementation. A milestone's issues
are its work packages; a completed milestone is closed. Retained deferred
milestones remain historical/deferred work, outside this active two-batch queue.

**Views**, set up once in GitHub's web interface:

- *Board*: columns by Status.
- *Milestones*: a table grouped by milestone.
- *Findings*: a table filtered to `label:"type: finding"`, showing labels.
- *Progression*: a table filtered to `label:"type: stage"`, sorted by Stage.

**Workflows**, also set up in the web interface: add every new repository issue
to the board with Status Backlog; set Status to Done when an issue closes or a
linked pull request merges. An agent that finds an issue missing from the board,
or a closed issue whose status was not updated, fixes it by hand.

## Issues and commits

- Title a work package `<milestone>: <work package>`, a finding
  `review-<commit> <id>: <summary>` (for example `review-e2c4fc2 L1: ...`), and a
  stage `Stage: <constructs>`.
- The body states the scope and completion criteria and links the roadmap
  section, the capability record and any evidence or review report. Detailed
  evidence stays in its record; the issue links it.
- Use sub-issues when one work package splits further. A milestone's order is
  recorded once, in the roadmap.
- A commit that advances an issue references it with `Refs #<n>`, and the commit
  that completes it uses `Fixes #<n>`, which closes the issue when the commit
  reaches `main`. Housekeeping with no issue needs no reference.

## Delivery batches

Keep one committed batch and one provisional successor in the active queue.
The roadmap states their order and authorization; the capability record holds
the design and evidence; the milestone and issues hold live work status.
Use existing records and board fields, without a second planning database.

Before implementing a batch, its capability plan names:

- The user-visible outcome and concrete Rosetta tasks, preserving required
  interfaces, ranges and outputs.
- Included forms and boundaries, dependencies and the common semantic/proof
  machinery that makes grouping useful.
- Meaningful implementation increments, each with an issue in the same milestone,
  scope, completion criteria and focused checks. Create the increment issues and
  record their order together; use sub-issues only when an increment itself splits.
- One shared final validation/review checkpoint, expected evidence reuse and
  the changes that would require fresh compiler/runtime or source-proof work.

Each implementation issue carries a short checklist for implementation, focused
verification, review and final evidence applicability. Batching does not make an
unfinished increment or unvalidated composition supported. Sample-only batches
still require application proof/build/execution and faithful task assessments.
Keep small commits or stacked PRs reviewable while sharing final validation.
If scope changes, update the issue and capability plan with the reason rather
than silently dropping a task or enlarging the batch.

At delivery, record actual Rosetta mappings gained, elapsed delivery time and
expensive checkpoint attempts, including failures/interruption and repair causes.
Link existing run records; distinguish pauses and overlapping runs without
building new metrics infrastructure. Use these observations to size the
provisional successor. Planning approval is separate from implementation
authorization, and neither replaces the existing merge authorization.

## Agent routine

The primary coding agent implements owner-authorized work. The planning agent
maintains the board, issues, Rosetta assessments and reviews. These roles do not
grant either agent authority to start work or amend the Oracle: only the owner
does that, with the decision recorded in session memory.

1. **Start of session.** Read the documents `AGENTS.md` lists, then the open
   issues of the current milestone and any open decisions:

   ```bash
   gh issue list --repo berkeleynerd/silver --state open --milestone "<milestone>"
   gh issue list --repo berkeleynerd/silver --state open --label "type: decision"
   ```

2. **Claiming work.** Start only Ready items with recorded owner authorization,
   or work the owner requests directly. Before starting an issue, check that
   another agent has not claimed it, then set it to In progress and comment with
   the branch or worktree.
   Parallel agents act as the same GitHub user, so the comment, not the assignee,
   identifies the session.
3. **Splitting work.** When a task splits into increments, create one issue per
   increment in its milestone, with scope and completion criteria, in the same
   planning step. Record the milestone's order and remaining decisions in the
   roadmap.
4. **Review findings and follow-ups.** File each material finding as an issue
   with `type: finding` and its severity. The review report remains the
   evidence. Its disposition (fixed, deferred with a reason or rejected with a
   reason) goes in the issue and, as before, in the capability record. When a
   follow-up's trigger occurs, preserve its evidence at once, before another run
   replaces the inputs or logs, and comment on the issue; a repair still needs
   authorization.
5. **Handoffs.** Comment on each affected issue with its state, evidence links
   and next step. Owner decisions and authorizations still go in the session
   memory. For proof work, identify the relevant managed run IDs, current
   diagnostic checkpoint and next smallest required check. Link the ledger and
   evidence instead of duplicating timing history; see the
   [proof-iteration record](proof-iteration.md).
6. **Completion.** Close the issue through its commit, and update the roadmap's
   capability/milestone completion record, `language.md`, the catalogue, samples
   and capability record together as [development.md](../development.md) requires.
   This records delivered support; live task status remains on the board.

Parallel streams use separate worktrees and branches. Preserve unrelated edits
and untracked files; never use a bare `git stash` in the shared checkout.
Python files in `scripts/` feed proof-provenance hashes, so unrelated tooling
belongs elsewhere.

## Rosetta progression

Each progression stage that becomes a near-term target gets one `type: stage`
issue, titled by the constructs it adds, with Constructs set and Stage holding its
current position. [rosetta/progression.md](../rosetta/progression.md) carries its
admission questions, failure paths and driver samples. Stage numbers change
whenever the progression is re-rendered, so update the Stage field after each
re-render for open and closed stage issues. Closed issues whose constructs are
now supported carry Stage 1; their Closed/Done status remains unchanged.
Do not put stage numbers in titles or links. Create stage issues
for the next few stages only, and sample sub-issues only for the active stage.

Generated stages and owner-selected milestones can differ. Record the mapping
in the roadmap and stage issue when a coherent milestone spans stages or admits
only part of a broad construct identifier. Keep the remaining forms and samples
explicit; do not mark the whole identifier supported until its assessed uses
are covered, or the identifier and assessments have been split to describe the
delivered fragment accurately. A re-render does not authorize the next stage.

When a milestone admits a construct, add its identifier to `supported` in
[rosetta/coverage.json](../rosetta/coverage.json), update the description of
today's Silver in `rosetta/assess.js`, run `python3 rosetta/refresh.py --render`,
and update the stage issue or close it if its constructs are all supported.
At delivery, also check the assessor's current-language description and the
affected assessment summaries/review metadata for stale prepared or pending
claims. Re-render changes to those source records; do not edit generated pages
independently.

## Access

Agents use the `gh` CLI with the sandbox's injected token, which needs the
classic scopes `repo` and `project`, plus `read:org` for the CLI. Issues, labels
and milestones need only `repo`; the board needs `project`. Views and workflows
cannot be created through the API and are configured in the web interface.
